# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Source of truth

**[AGENTS.md](AGENTS.md) is the authoritative spec** — architecture, folder structure, domain map, security/RBAC model, conventions, and Definition of Done all live there. Read it first and follow it. This file only records where the current repo **diverges from that target** and the concrete commands, so it does not repeat AGENTS.md.

## Current state vs. the AGENTS.md target

AGENTS.md describes the **target**. These are the deliberate, still-standing divergences (structure and layering inside each app already follow the spec):

- Apps live in **`backend/`** and **`frontend/`**, not `apps/api` / `apps/web`. There is **no pnpm workspace root** and no `packages/api-contract` — each app is installed, built, and tested on its own (`cd` into it), and there are no root-level scripts. The frontend therefore **hand-writes its API types** under each feature's `models/` (see `core/models/api-response.models.ts`), derived from the Swagger.
- The backend DB layer supports **MySQL *and* PostgreSQL**, chosen at runtime by `DB_TYPE` (MySQL/cPanel is the live deployment). IDs are **app-generated UUID v4 stored as `varchar(36)`** (`common/entities/base.entity.ts`) so the schema is portable — no `uuid` column type, no DB extension.
- Password hashing uses **`bcryptjs`** (pure JS), not `bcrypt` — chosen so cPanel needs no native build.
- **Response envelope** is `{ success, statusCode, message, content }` / `{ success, statusCode, message, errorCode?, errors[] }` (`common/types/api-response.types.ts`), not the flat shape in AGENTS.md §6. `errorCode` comes from `common/types/error-code.enum.ts` and is the stable contract the frontend switches on.
- **El aspirante es multipaís; la empresa y la vacante, no (T36).** Un candidato puede ser de **México, Colombia, Estados Unidos o Canadá**: su país de residencia (`candidate_profiles.country`, ISO 3166-1 alpha-2) decide qué subdivisiones y qué **tipos de documento** valen, y el teléfono se guarda en **E.164 con su país en columna aparte** (`phone_country`) porque `+1` es Estados Unidos **y** Canadá y el número no los distingue. Los catálogos viven en `backend/src/common/catalogs/{countries,country-subdivisions,identity-documents}.ts`, espejados en `frontend/src/app/shared/catalogs/countries.catalogs.ts`. ⚠️ **Todo lo demás sigue siendo mexicano y es deliberado**: RFC, C.P. de 5 dígitos, régimen SAT, uso de CFDI, `vacancies.state`, las landings `/trabajo/<área>-en-<estado>`, MXN e IVA 16 %. Si vas a "internacionalizar" algo de eso, es otra tarjeta, no una mejora de paso. Tres trampas concretas: (1) **los códigos de subdivisión colisionan entre países** — `GUA` es Guanajuato (MX) y Guainía (CO), `DC` es District of Columbia (US) y Bogotá D.C. (CO) —, así que `subdivisionName(country, code)` **siempre** pide el país y `stateBySlug()`/`stateSlugOf()` de `shared/utils/seo.ts` sólo valen para vacantes; (2) los códigos de documento llevan prefijo de país salvo `PASSPORT`, y **no se ofrece SSN ni SIN** para US/CA (decisión con implicación legal, ver `identity-documents.ts`); (3) la unicidad del documento es `(document_country, document_type, document_number)`, no el número a secas. Las reglas cruzadas país↔subdivisión↔documento están en **un solo sitio**, `common/validators/candidate-identity.validator.ts`, y lanzan `AppException` con `UNSUPPORTED_COUNTRY` / `INVALID_SUBDIVISION` / `INVALID_DOCUMENT_NUMBER` / `INVALID_PHONE` **desde el caso de uso y no desde un validador de `class-validator`**: la tubería de validación devuelve siempre `VALIDATION_ERROR`, y el registro necesita el código concreto para saltar al paso del asistente donde está el campo. El teléfono se pinta con **`ij-phone-input`**, cuyo valor es un **objeto** `IjPhoneValue` (`{country, national, e164}`) y no la cadena E.164 — con la cadena, `writeValue('+14155550123')` no podría saber si pintar «Estados Unidos» o «Canadá»; se convierte con `toPhonePayload`/`fromPhonePayload` de `shared/utils/phone.ts`. En la empresa se usa el mismo control con `[lockCountry]="true"`. Plan completo: [Impulso_Jobs_Multipais_Candidatos.md](Impulso_Jobs_Multipais_Candidatos.md).
- **Catalogs are not a `modules/catalogs/` group.** MX states/municipios, SAT tax regimes, CFDI uses **and the 23 professional areas (T15)** are embedded constants in `backend/src/common/catalogs/` (mirrored in `frontend/src/app/shared/catalogs/` — `mx.catalogs.ts`, `professional-areas.catalogs.ts`); `languages` is an entity inside `modules/candidates/`. Professional-area ids are stable and never reordered; their `slug` feeds the SEO landings (`/trabajo/<area>-en-<estado>`).
- **Texto enriquecido de la vacante (T32): se sanea al guardar, no al pintar.** `description`, `requirements` y `responsibilities` guardan **HTML** desde T32; las vacantes anteriores siguen en texto plano y **no se migraron**. En el backend, los tres campos llevan `@RichText({ max, required })` (`common/decorators/`), que sanea con `sanitizeRichText` **antes** de validar — así no se puede añadir un campo largo y olvidarse de limpiarlo, y el tope cuenta caracteres de contenido, no de marcado. En el frontend se pinta con `ij-rich-text`, que **detecta si el valor es HTML o texto plano** y elige el render; `[innerHTML]` de Angular sanea como segunda capa. ⚠️ **El `description` del JSON-LD y la `<meta description>` van en texto plano** (`toPlainText` / `excerpt` de `shared/utils/rich-text.ts`): el JSON-LD vive dentro de un `<script>` y un `</script>` en la descripción se escaparía del bloque — eso Angular **no** lo cubre. Si añades un cuarto campo largo, dale `@RichText` y píntalo con `ij-rich-text`.
- **CKEditor sólo se carga en el navegador, vía `@defer`.** `ij-editor` no importa `ckeditor5`: referencia `IjCkeditorHost` **dentro de un bloque `@defer`**, y Angular convierte eso en un `import()` dinámico que no se ejecuta en el servidor. Con un import normal el build falla al extraer rutas con `t.createElement is not a function`, aunque `/empresa/**` sea `RenderMode.Client` — la extracción de rutas evalúa los módulos en Node igualmente. El CSS de CKEditor (~219 KB) se importa en la hoja de `ckeditor-host.css` y no en `angular.json`, para que viaje en ese chunk y no lo cargue el portal público; por eso el presupuesto `anyComponentStyle` de `angular.json` está subido. ⚠️ **Esa transformación de `@defer` sólo se aplica con la optimización activada, es decir en el build de producción — no en `ng serve`.** Por eso las opciones de SSR (`outputMode`, `ssr`, `server`) viven en la configuración **`production`** de `angular.json` y no en las opciones base: con ellas en la base, `pnpm start` extraía rutas en Node con el import de CKEditor todavía estático y **todas** las rutas fallaban con `domDocument.createElement is not a function` (500 en cualquier página, no sólo en las del editor). Consecuencia a tener presente: **`pnpm start` sirve sólo en cliente**; para probar SSR, i18n por cookie o el SEO hay que usar `pnpm run build` + `pnpm run serve:ssr:frontend`, que es lo que se despliega. ⚠️ **La licencia es `'GPL'`**, que obliga a que la app sea GPL: es deuda legal consciente hasta contratar la licencia comercial (ver TASKS.md · T32).
- **El plan de una empresa se gestiona desde `billing/`, no desde `companies/` (T34).** Las rutas `/admin/companies/:companyId/subscription` (`GET`/`POST`/`PATCH`/`DELETE`) viven en `billing/controllers/admin-company-subscriptions.controller.ts` porque **`BillingModule` ya importa `CompaniesModule`**: meterlas en `AdminCompaniesController` cerraría un ciclo de DI, igual que `GET /auth/me`. En el sentido contrario, el listado del back-office sí necesita *leer* el plan, y lo hace con `ICompanyPlanRepository` (`companies/repositories/`) sobre las entidades `CompanySubscription` y `Plan` **en sólo lectura y en lote** — importar una clase de entidad no crea ciclo, importar el módulo sí. **Escribir sobre la suscripción es exclusivo de `billing`**, que es quien conoce los cupos y la activación.
- **Toda alta de suscripción pasa por `SettlePaymentUseCase`,** venga del autoservicio o del administrador. La asignación manual crea la suscripción y su orden, abre el cobro por `PaymentProviderPort` y liquida — no escribe el alta a mano. Un alta "por la izquierda" dejaría a la empresa con plan pero **sin cupo de la base de talento**, que es lo que otorga `EntitlementService.grantTalentVisits()` desde ese caso de uso.
- `POST /auth/register` lives in its own **`modules/iam/registration/`**, not inside `iam/auth/`. Igual `GET /auth/me` (T27), que vive en **`modules/iam/session/`**: resuelve el nombre y la imagen leyendo de `candidates` y `companies`, y esos módulos importan `AuthModule` — meterlo en `AuthController` cerraría un ciclo de DI. Mismo motivo que `AdminUsersModule` y `AccountModule`. **Todo endpoint nuevo bajo `/auth` que necesite leer un dominio va aquí, no en `auth/`.**
- **El nombre de una persona vive en `users`, pero no siempre manda.** Hasta ahora `users` no tenía columna de nombre y el nombre para mostrar se derivaba: candidato → `candidate_profiles.first_name + last_name`; empresa → `companies.business_name`; **ADMIN → nada**, así que el back-office podía editarlo todo de una cuenta administrativa menos quién era. `users` lleva ahora `first_name`, `last_name`, `phone`, `job_title` y `photo_url`. La precedencia la fija `toUserResponse`: **si `UserProfileResolver` resuelve un nombre desde el perfil, ese gana**; lo de `users` es el respaldo, y para un ADMIN es lo único que hay. Por eso el modal de `/admin/usuarios` **no pinta la sección Identidad cuando el rol es candidato** — su nombre se edita en *Perfil del aspirante* y duplicar el campo dejaría dos orígenes para el mismo dato. La columna es `job_title` y no `position` porque POSITION es palabra reservada del estándar SQL y el esquema tiene que valer en MySQL y en PostgreSQL.

- **Las tablas del back-office son `ij-table`, sobre TanStack Table en modo headless.** `@tanstack/angular-table` aporta el orden, la selección y el modelo de filas; **el marcado y las clases son del kit `ij-*`**, así que no entra una segunda hoja de estilos ni un segundo sistema de diseño (fue la razón de descartar PrimeNG para esto). El contenido de cada celda lo pone el consumidor con `<ng-template ijCell="<id>" [ijCellOf]="filas()" let-fila>`; **`ijCellOf` no se usa en ejecución**, existe para que Angular infiere el tipo y `let-` no caiga a `unknown`. Dos modos: `sortMode="client"` (TanStack ordena; para listas completas — planes, roles, equipo de empresa) y `sortMode="server"` (sólo refleja el estado y avisa; para listados paginados — usuarios, empresas). ⚠️ **En un listado paginado nunca se usa `client`**: ordenaría las 10 filas de la página y el orden sería falso sobre el total. **Pásale siempre `rowId`**: sin él TanStack identifica la fila por su índice y la selección salta a otra fila al reordenar.
- **Las tres áreas privadas comparten un único shell: `layout/app-shell/`.** `/admin`, `/empresa` y `/candidato` no tienen cada una su riel, su miga de pan y su menú de sesión — tienen el mismo componente y le pasan datos (`navItems`, `menuItems`, `sectionLabel`, `breadcrumbRoot`, `homeRoute`, `roleLabel`, `notificationsRoute`, `storageKey`). Los tres layouts quedan en 50–90 líneas de configuración. Lo que de verdad difiere entra por proyección: el pie del riel del candidato (`[shellRailFooter]`). ⚠️ **`storageKey` es distinta por área** — plegar el back-office no tiene por qué plegar el panel de la empresa. ⚠️ **Nombre y foto:** por defecto salen de la sesión (`GET /auth/me`); un área puede imponer los suyos (`displayName`/`avatarUrl`) y el candidato lo hace con su ficha, que es la que él edita y se refresca al instante. Si añades un input nuevo, dale respaldo de sesión como tienen `name()` y `avatar()`, o las áreas que no lo pasen se quedan sin ese dato.
- **El patrón de listado vale para las tres áreas, pero sólo donde hay tabla.** Cabecera de 28px + tarjeta única con filtros arriba, tabla en medio y paginación de pie; pestañas subrayadas donde hay solapas (usuarios, denuncias, postulaciones de empresa). ⚠️ **Donde el listado es una rejilla de fichas y no una tabla** —`/empresa/candidatos`, los planes de `/empresa/promociones`, `/candidato/{postulaciones,guardadas}`— **la barra de filtros se queda como tarjeta suelta**: no hay tabla a la que pegarla, y unirla a una rejilla no significa nada. Lo que sí se unifica ahí son las alturas (42px) y que la tarjeta lleve `border border-line`.

- **El listado de `/admin/usuarios` va en una sola tarjeta: filtros + tabla + paginación.** Los tres operan sobre el mismo listado, así que comparten caja. Lo hacen posible tres entradas opcionales añadidas para esto —`[bare]` en `ij-table`, `admin-table-skeleton` y `admin-error` (quitan borde/radio/fondo propios), y `[inCard]` en `admin-pagination` (cambia el margen por un pie con borde superior)—; **todas con `false` por defecto**, así que el resto del back-office no se entera. Las pestañas van subrayadas encima de la tarjeta. ⚠️ Una pestaña subrayada necesita `overflow-y-hidden` junto a `overflow-x-auto`: CSS fuerza `overflow-y: auto` cuando el otro eje no es `visible`, y el `-mb-px` que monta el subrayado sobre el borde deja el contenido 1px más alto que la caja — Chrome saca una barra de desplazamiento vertical al lado de las pestañas. **Los cinco listados de `/admin` (usuarios, empresas, planes, roles, denuncias) siguen ya este patrón**, así que al añadir uno nuevo se copia de cualquiera de ellos. Las barras de filtros llevan los controles a **42px**, que es la altura de `ijControlClass`: así un `ij-select` —el filtro por estado de empresas son las 32 entidades, que no caben en pastillas— cae al lado sin desalinearse. Planes y denuncias conservan una `<table>` a mano en vez de `ij-table`; si las migras, acuérdate de que la cabecera de `ij-table` va con `bg-surface/60`.
- **`ij-modal` tiene modo `[scrollable]`** (por defecto `false`, que desplaza la página entera). Acota el panel a la ventana y desplaza **sólo su cuerpo**, de modo que un pie con `sticky bottom-0` dentro del formulario se queda a la vista — el contenedor de desplazamiento es el cuerpo, no la página. Es lo que usa el alta de usuario, que son tres secciones. **No hay ranura de proyección para el pie a propósito**: el pie vive dentro del `<form>` del componente hijo, y proyectarlo lo sacaría del `<form>` en el DOM, rompiendo `type="submit"`.
- **El riel de `/admin` se pliega y lo recuerda** (`localStorage`, clave `ij-admin-sidebar`). La cabecera lleva miga de pan derivada de la URL y menú de sesión. El contador de denuncias pendientes se pide **una vez por carga del área** y no se refresca al resolver una denuncia: vuelve a cuadrar al recargar.

- **Ordenar por columna exige lista blanca en el backend.** `sortBy`/`sortOrder` llegan por query string, y `buildOrder` (`common/utils/sort.util.ts`) sólo los acepta si la clave está en el mapa de columnas del listado (`USER_SORT_COLUMNS`, `COMPANY_SORT_COLUMNS`, `VACANCY_REPORT_SORT_COLUMNS`): lo que manda el cliente es una **clave**, nunca un nombre de columna, así que no puede acabar en el `ORDER BY`. El DTO hereda de `SortableQueryDto` y declara su propio `sortBy` con `@IsIn`. `buildOrder` añade además el orden por defecto como **desempate estable**: sin él, ordenar por una columna con valores repetidos (estado, rol) deja la paginación indefinida y una misma fila puede salir en dos páginas o en ninguna. **Una columna marcada `sortable` en el frontend cuya clave no esté en el mapa del backend queda muerta en silencio** — el backend la ignora y devuelve el orden por defecto.

- **Un avatar se pinta con `ij-avatar`, nunca con un `<img>` a pelo.** Cae a las iniciales del nombre tanto si no hay foto como si **la URL guardada ya no sirve** (escucha el `error` de la imagen). Ese segundo caso no es raro: las imágenes se persisten absolutas (T23), así que un cambio de host deja filas apuntando al anterior hasta que se corre `uploads:rehost`, y sin el respaldo el hueco se llena con el icono de imagen rota del navegador. Tamaño, radio y colores los pone el consumidor con clases sobre el host.

- **«Mi cuenta» es una sola página para las tres áreas** (`/admin/mi-cuenta`, `/empresa/mi-cuenta`, `/candidato/mi-cuenta`, todas sobre `features/account/`). Puede serlo porque `/account/**` **no lleva id**: el backend resuelve al titular desde el token, así que lo único que cambia por área es el shell. Se llama `mi-cuenta` y no `perfil` porque `/empresa/perfil` es la ficha fiscal de la empresa y `/candidato/perfil` el perfil profesional del aspirante — son otra cosa y ya existían. ⚠️ **A un CANDIDATE no se le ofrecen los campos de nombre, teléfono ni foto**: los suyos viven en `candidate_profiles` y es de ahí de donde los lee todo lo demás (`UserProfileResolver`), así que duplicarlos aquí dejaría dos orígenes para el mismo dato y lo que escribiera no se vería en ningún sitio; la página le enlaza a *Perfil del aspirante*. Misma regla que ya aplicaba el modal de `/admin/usuarios`. **El correo no se edita** en ningún rol: cambiar la identidad de acceso sin re-verificar la dirección nueva convierte una sesión robada en una toma de la cuenta.
- **`POST /account/password` cierra todas las sesiones, incluida la que llama.** Mueve `tokensValidFrom`, así que el token con el que se hizo la petición deja de valer al instante: el formulario **avisa antes** y la página cierra sesión y manda a `/auth/login?passwordChanged=1`, que pinta el aviso. Si añades otro endpoint que re-autentique pidiendo la contraseña en el cuerpo, recuerda las dos piezas — el aviso previo y el destino posterior.
- **Un 401 no siempre significa "tu sesión caducó".** Un endpoint que re-autentica al titular (cambio de contraseña, baja de cuenta) responde 401 con `AUTH_INVALID_CREDENTIALS` cuando la contraseña del cuerpo es incorrecta, y ahí la sesión está viva. `refresh.interceptor.ts` excluye ese `errorCode` de su lógica de renovación: sin la exclusión renovaba el token (con éxito), reintentaba, volvía a recibir 401 y **cerraba la sesión** — el usuario se equivocaba al teclear su contraseña y aparecía en el login sin explicación. Si creas otro código de error para un fallo de re-autenticación, añádelo a `NO_REFRESH_ERROR_CODES`.
- **`GET /auth/me` resuelve el nombre por precedencia: perfil de dominio primero, `users` de respaldo.** Candidato → `candidate_profiles`; empresa → `companies.business_name`; ADMIN no tiene perfil de dominio, así que su identidad **es** la de `users`. El respaldo no existía hasta que se añadió «Mi cuenta»: desde que `users` tiene `first_name`/`last_name`/`photo_url`, el back-office podía ponerle nombre a una cuenta administrativa y su propia cabecera seguía enseñando el correo. ⚠️ **La foto sigue la precedencia contraria: manda `users.photo_url`**, con la del dominio de respaldo. Un nombre comercial responde a "en representación de quién actúo"; un avatar responde a "quién soy", y quien sube su foto en «Mi cuenta» espera verla. Quien no suba ninguna conserva la que tenía (logo de empresa, foto de aspirante), así que no hay regresión. Está cubierto por `get-current-user.use-case.spec.ts` — si alguien iguala las dos precedencias, falla. Consecuencia viva: **el nombre personal de un EMPLOYER no se ve en la cabecera** de `/empresa`, donde gana el nombre comercial. Donde sí se ve es en el equipo: `CompanyMemberResponseDto` expone `displayName`, `jobTitle` y `photoUrl`, y las dos tablas de equipo (`/empresa/usuarios` y la ficha de `/admin/empresas/:id`) pintan la persona con el correo debajo, cayendo al correo cuando aún no ha puesto nombre. Ambas salen del mismo `CompanyMembersUseCase`, así que se tocan a la vez.

- **Autorizar exige rol *y* permiso.** `@RequirePermissions` dice *qué* se puede hacer, pero varios roles comparten un permiso —una empresa tiene `companies.read` y `company_users.manage` sobre **la suya**—, así que por sí solo no separa el back-office del autoservicio. Los tres controladores `/admin/**` llevan además `@RequireRoles(Role.ADMIN)` + `RolesGuard`; sin eso un EMPLOYER listaba todas las empresas y leía el equipo de la competencia. **Todo endpoint nuevo bajo `/admin` debe llevar los dos.** El gemelo autoservicio de `/admin/companies/:id/members` es `company/members`, donde la empresa **nunca viaja en la URL**: se resuelve de la sesión (`resolveOwnCompanyId`), y gestionar el equipo pide además rol interno OWNER/ADMIN.
- Frontend adds areas AGENTS.md does not list: **`features/candidate/`** + `layout/candidate-layout/` (el área real del candidato: `/candidato/{perfil,cv,postulaciones,guardadas,configuracion}` — sustituyó al prototipo `/panel`, eliminado en la Parte A) and **`features/company/`** + `layout/company-layout/`. `ROLE_HOME`: admin → `/admin`, empresa → `/empresa/vacantes`, candidato → `/candidato/perfil`.
- **El detalle público es `/vacantes/<uuid>-<slug>` (T16).** La ruta sigue siendo `:id`; el UUID son los primeros 36 caracteres del parámetro y el slug es sólo SEO. Construye links con `vacancyPath()` de `shared/utils/seo.ts`, nunca a mano.

### What is built (Aug 2026)

- **Backend** — `modules/`: `iam/{auth,users,roles,permissions,registration,account,session}` (`account/` cubre ahora también identidad, contraseña y foto propias), `notifications`, `candidates`, `companies`, `vacancies`, `applications`, `talent`, `billing`, `audit`. 31 controllers, 70 use-cases, 32 migrations, 50 unit specs. Swagger at `/docs` + `/docs-json`, global prefix `/api/v1`. Includes screening questions (M15/T10), denuncias (T12), vacante enriquecida con área/contrato/escolaridad/plazas/comisiones/fecha límite + filtros y orden públicos (T15), vigencia con `expires_at` + job (T20), contador de vistas con eventos + consolidación (T18), snapshot del CV al postular (T19) vacantes guardadas del candidato (T17 fase 1, permiso nuevo `saved_vacancies.manage`) identidad de la sesión en `GET /auth/me` (T27), gestión del plan de una empresa desde el back-office (T34) y responsabilidades de la vacante en HTML saneado (T32), notificaciones en plataforma + correo con adaptador SMTP real (T21), vencimiento de suscripción con avisos escalonados idempotentes (T22), imagen de referencia de la vacante (T24), skills requeridas normalizadas en `skills` + `vacancy_skills` (T25) y **aspirantes de MX/CO/US/CA con teléfono E.164 por país y documento por país emisor (T36)**.
- **Not built** — the **Stripe adapter** (billing itself is done; payments go through `PaymentProviderPort`, today bound to `ManualPaymentAdapter`), CFDI, AI, `sitemap.xml`, T17 fases 2+ (ocultar/seguir/alertas). No e2e tests yet. **El backlog acordado está detallado en [TASKS.md](TASKS.md) § Parte C — T21–T27 hechas; queda T28**, que recoge lo que T26 dejó fuera a propósito: las **áreas privadas** (`/candidato`, `/empresa`, `/admin`, todavía sólo en español) y el **idioma de los correos**. No está bloqueada técnicamente, sino por una decisión de negocio (N10: si alguien va a usar el panel en inglés) — **y desde T36 pesa más**: abrir el registro a Estados Unidos y Canadá deja a esos aspirantes con un panel sólo en español.
- **`candidates/` vs `talent/`** — `candidates/` is the applicant's self-service over their own data; `talent/` is the company-facing side (searching third parties, consuming purchased visit quota). `talent/` owns `talent_access_grants`/`talent_access_views` and the *consumption*; `billing/`'s `EntitlementService` does the *granting* when a payment settles. ⚠️ **`GET company/candidates/:id/resumes/:resumeId` (T30) es la excepción: no consume ni exige cupo**, por decisión de negocio del 2026-09-12 — valida permiso, visibilidad del perfil y pertenencia del CV, nada más. Está anotado en el JSDoc de `getResumeDownload`; si añades otro endpoint que sirva datos del banco de talento, **el que cobra sigue siendo el detalle** (`get()`), no éste.
- **Payments go through a port.** `billing/` never imports Stripe: it depends on `PaymentProviderPort`, bound to `ManualPaymentAdapter` in `billing.module.ts` (same pattern as `MAILER_PORT`). Every payment — webhook, manual confirmation or reconciliation — funnels through `SettlePaymentUseCase`, which owns idempotency (`processed_payment_events`) and activation. Writing `StripePaymentAdapter` is a one-line binding change.
- **Frontend** — public portal (home, vacantes con SSR + landings `/trabajo/...`, planes, nosotros, contacto, faq, mantenimiento), auth (login, registro empresa/candidato, reset, verificación), `/admin` (usuarios, empresas, roles, planes, denuncias), **`/empresa` completo** (vacantes, postulaciones, candidatos, promociones, usuarios, perfil) y **`/candidato`** (perfil, cv, postulaciones, guardadas, configuración). **Todo el back-office edita en `ij-modal`**, no en páginas de formulario: el detalle en ruta propia queda sólo para lo que no cabe en un diálogo (matriz de permisos del rol, equipo de la empresa). UI kit is `ij-{input,select,multiselect,autocomplete,datepicker,phone-input,textarea,editor,rich-text,modal,pdf-viewer,table,avatar,badge,button,icon,logo,password-strength,pricing-card}` — **no** `card`/`pagination`/`tabs`/`spinner`/`empty-state` yet (admin uses a local `admin-pagination`, panel a local `data-table`). El **alta y la edición de vacante son la tercera excepción al `ij-modal`** (T32): 19 campos, tres editores enriquecidos y las habilidades no caben en un diálogo, así que viven en `/empresa/vacantes/nueva` y `/empresa/vacantes/:id/editar` como un wizard de 4 pasos con borrador en `localStorage`. `ij-pdf-viewer` (T30) es la **segunda excepción al `ij-modal`**: un overlay a pantalla completa porque una hoja A4 no cabe en los 900px del diálogo más grande. Renderiza con `<iframe>` sobre un blob URL, sin librería, y degrada a "Abrir en pestaña nueva" en iOS y por debajo de 768px. Lo usan `/empresa/{postulaciones,candidatos}` y `/candidato/cv`.

## Semillas y datos de catálogo

**Regla de oro: los datos que ya existen se siembran con `pnpm seed`; los datos *nuevos* entran por migración.** Un seeder depende de que alguien se acuerde de ejecutarlo — y cuando no se ejecuta, la app responde 403 o se queda sin catálogo sin avisar (es exactamente el fallo de T29). Una migración corre sola en el despliegue, deja constancia en la tabla `migrations` y no se repite.

### Las seis semillas existentes: un comando

```bash
cd backend
pnpm run seed            # catálogos + administrador — seguro en cualquier entorno
pnpm run seed:demo       # lo anterior + cuentas de prueba (candidato y empresa)
pnpm run seed -- --list  # qué hay y qué hace cada una
```

- Orquestador en `src/database/seed.ts`. Abre **una sola conexión** para las seis y respeta el orden (RBAC primero: crea los roles que el resto asigna). Si una falla, dice **cuál** y aborta; las siguientes no corren.
- Filtros: `-- --only=rbac,admin` · `-- --skip=plan-features`. `-- --demo` añade las cuentas de prueba, y **se bloquea con `NODE_ENV=production`** salvo `--force`: `pnpm seed` en un servidor no siembra basura.
- Gemelos compilados: `seed:prod` y `seed:demo:prod`. **Los scripts individuales siguen existiendo** (`seed:rbac`, `seed:admin`, …, con sus `:prod`) — cada `seed-*.ts` exporta su función y sólo se auto-ejecuta si se invoca directamente (`require.main === module`).
- **Todas son idempotentes y actualizadoras**: insertan lo que falta y refrescan lo existente (nombres, descripciones, orden). Correrlas dos veces no duplica nada.
- Lo que `seed:rbac` **no** hace: retirar permisos. Quitar un código de `MATRIX` no borra la fila de `role_permissions`, porque un borrado en ciego arrasaría también los permisos que un admin haya dado a mano en `/admin/roles`. Para revocar, hazlo desde el back-office o con una migración de datos.
- `seed:plan-features` siembra los 13 códigos de beneficio pero **ningún plan**: los precios en MXN son decisión de negocio y se capturan en `/admin/planes`.
- ⚠️ **Tras sembrar contra un servidor en marcha hay que reiniciar el proceso.** `PermissionsService` cachea el mapa rol→permisos en memoria y el seed escribe en la BD por fuera de la app: sin reinicio, los permisos nuevos siguen dando 403.

### Reparar datos ya guardados

También va por migración, y el patrón está en `1720000030000-RepairMojibakeText.ts`: un barrido previo sobre **todas** las columnas de texto para saber qué hay, y luego reemplazos de **fragmento** acotados a la columna donde apareció cada uno (`REPLACE(col, roto, bueno) WHERE col LIKE '%roto%'`), con el texto roto pasado como **parámetro** y no como literal — el driver lo transporta sin depender de la codificación del cliente, que es justo lo que corrompió esos datos en su día.

Dos cosas que conviene no olvidar de aquel caso:

- **U+FFFD no es doble codificación.** `Ã³` por `ó` es reversible byte a byte; `□` significa que el byte original **ya se perdió** y sólo consta que ahí había un carácter. No hay deducción automática: la corrección se escribe a mano, palabra por palabra. Antes de asumir una cosa u otra, mira si el valor trae `Ã`/`Â` (recuperable) o `□` (no).
- **`down()` vacío y con el motivo escrito.** Revertir una reparación obligaría a buscar el texto *correcto* para volver a romperlo, y esa búsqueda alcanzaría también a las filas que nacieron bien. No tiene valor y sí daño cierto.

⚠️ La corrupción **no venía de las semillas** (`seed-candidate.ts` escribe bien «Cuauhtémoc»), sino de escrituras hechas desde una consola con la codificación equivocada. Si vuelves a ver `□` en la BD, sospecha de un `curl` o un script lanzado desde una terminal Windows antes que del código.

### Datos nuevos: siempre una migración

Añadir una fila a un catálogo (un estado de postulación, un beneficio, **un permiso nuevo**) se hace con una migración de datos, no tocando un seeder. Usa `src/database/migrations/helpers/seed-data.helper.ts`:

```ts
import { upsertSeedRows, deleteSeedRows } from './helpers/seed-data.helper';

const ROWS = [{ code: 'HIRED', name: 'Contratado', sort_order: 8, is_final: true }];

export class AddHiredApplicationStatus1720000026000 implements MigrationInterface {
  name = 'AddHiredApplicationStatus1720000026000';

  public async up(q: QueryRunner): Promise<void> {
    await upsertSeedRows(q, { table: 'application_status', matchBy: ['code'], rows: ROWS });
  }

  public async down(q: QueryRunner): Promise<void> {
    await deleteSeedRows(q, { table: 'application_status', column: 'code', values: ROWS.map((r) => r.code) });
  }
}
```

- `upsertSeedRows` es **idempotente**: inserta si falta, actualiza si está. Así convive con una BD donde el seeder equivalente ya pasó. Con `updateColumns: []` inserta pero no pisa lo existente — útil cuando el back-office puede haber editado el dato.
- Rellena solo el `id` (UUID v4 en Node, como `BaseEntity`) y `created_at`/`updated_at`. Desactivables con `withId` / `withTimestamps`.
- **Nada de entidades ni repositorios dentro de una migración.** Una migración es inmutable: describe el esquema del día que se escribió. Si importara una entidad, un cambio futuro en esa entidad rompería una migración vieja. Por eso el helper es SQL con nombres literales.
- Portable MySQL/PostgreSQL: identificadores escapados con el driver y parámetros con `createParameter` (`$1` en PG, `?` en MySQL). Escribir `"tabla"` a mano revienta en MySQL con ER_PARSE_ERROR 1064.
- El helper vive en `migrations/helpers/`, **no** en `migrations/`: el glob del `AppDataSource` es `migrations/*{.ts,.js}` y no cruza subdirectorios, así que no se intenta ejecutar como migración.
- Sigue aplicando lo de siempre: **numera la migración mirando primero el directorio** (los timestamps son correlativos a mano).

## Tooling notes (not in AGENTS.md)

- **Path aliases** use `@/` in both apps but with **different targets** — Backend: `@/*` → `src/*` (resolved by the Nest CLI at build, no `tsc-alias`; Jest via `moduleNameMapper`). Frontend: `@/*` → `src/app/*` (resolved by the Angular build from `tsconfig.json` `paths`). Prefer `@/…` over `../…` for cross-directory imports; keep `templateUrl`/`styleUrl` relative (the alias does not apply to component resource URLs).
- **Numera las migraciones mirando primero el directorio.** Los timestamps son correlativos a mano (`17200000NN000`), no generados, así que dos ramas en paralelo se llevan el mismo hueco con facilidad: pasó entre `InitVacancySkills` (T25) e `InitSubscriptionNotices` (T22), ambas en `1720000023000`. Dos migraciones con el mismo timestamp dejan el orden de ejecución indefinido. Si al resolver un merge te topas con un duplicado, renumera **la que menos entornos haya tocado** y reetiqueta su fila en la tabla `migrations` (`timestamp` y `name`) de las BD donde ya corrió, o intentará crear de nuevo lo que ya existe.
- **`sanitize-html` está fijado en 2.16.0 a propósito.** A partir de 2.17 arrastra `htmlparser2@12`, que es **sólo ESM**: Jest lo rechaza con `Cannot use import statement outside a module` y en un backend CJS desplegado en cPanel depende de la versión de Node. La 2.16 usa `htmlparser2@8`, que es CommonJS. Si subes la versión, comprueba antes `pnpm test -- rich-text`.
- **pnpm 10 blocks native build scripts.** Approved ones are pinned per app under `package.json` → `pnpm.onlyBuiltDependencies` (backend: none — the list is empty on purpose, there are no native deps; frontend: `esbuild`, `@parcel/watcher`, `lmdb`, `msgpackr-extract`). When adding a native dep, add it there and run `pnpm rebuild <pkg>`.
- **Frontend SSR (reactivado en T16):** `src/main.server.ts` must pass the `BootstrapContext` to `bootstrapApplication` (required since Angular 20.1) or the build fails at route extraction with `NG0401`. **Desde T26 el portal entero y `/auth/**` se sirven con `RenderMode.Server`** (sólo `/mantenimiento` y el catch-all siguen prerenderizados): un HTML estático se congela en un idioma en tiempo de build, así que la cookie de idioma no podría influir. Las llamadas a la API al iniciar siguen dentro de `afterNextRender`, **salvo** `/vacantes`, `/vacantes/:id` y `/trabajo/:landing`, que sí piden datos en el servidor y se los pasan al cliente por `TransferState` (ver `vacancies-page.ts` / `public-vacancy-detail-page.ts`; lo de navegador —compartir, mapa, preguntas— se queda en `afterNextRender`). **`security.allowedHosts` en `angular.json` es obligatorio** (hostnames sin puerto): sin el host listado, el motor SSR de Angular 20 lo rechaza y sirve CSR silenciosamente. SEO por vista con `core/services/seo.service.ts` (title/meta/OG/canonical/JSON-LD).
- **i18n (T26):** **Transloco** con diccionarios JSON en `frontend/src/app/core/i18n/translations/{es,en}.json`, cargados con `import()` (un chunk por idioma; el loader HTTP de Transloco no sirve en SSR). El idioma vive en la **cookie `ij_lang`** —`localStorage` no viaja en la petición, así que el servidor no podría saberlo— y `?lang=en` manda sobre ella: existe para dar **URL propia a cada variante**, que es lo que hace posible el `hreflang` que emite `seo.service.ts`. En plantilla se traduce con `*transloco="let t"`; **en código, siempre con `AppTranslateService`** (`core/i18n/`), que lee la señal de idioma antes de traducir y por eso un `computed` que lo use se recalcula al cambiar de idioma — `TranslocoService.translate()` a secas no. Fechas e importes, con `LocaleFormatService`, no con `Intl.*('es-MX')` a mano ni con los pipes de Angular (`LOCALE_ID` se resuelve una sola vez). **Al añadir texto nuevo, añade la clave en los dos ficheros**: `translations.spec.ts` falla si un idioma se queda atrás. No se traducen los catálogos ni lo que escriben los usuarios o el back-office (nombre de plan, título de vacante…).
- **cPanel:** the frontend deploys as a **Node SSR app** (`dist/frontend/server/server.mjs`; opción estática documentada pero pierde SSR) and the backend as a Node app on a subdomain — see [DEPLOY-CPANEL.md](DEPLOY-CPANEL.md). Set `DB_TYPE=mysql` with `DB_SYNCHRONIZE=false` in production and run `migration:run:prod` + the `:prod` seeds. **El correo saliente ya existe (T21)** — `MAILER_PORT` vive en `common/mailer/` (transversal, no en `iam/auth`) y `createMailerAdapter` (en `mailer.module.ts`) elige adaptador **por configuración**, en este orden: `RESEND_API_KEY` → `ResendMailerAdapter`; `SMTP_HOST` → `SmtpMailerAdapter` (nodemailer, legado); ninguna → `ConsoleMailerAdapter`, que escribe el correo en el log. **El proveedor es Resend**: define `RESEND_API_KEY` y `MAIL_FROM` (dominio verificado en Resend, SPF+DKIM) en el `.env` de producción; no hay que tocar código. El adaptador usa el **SDK oficial `resend`** (`new Resend(key).emails.send()`). Hasta la migración hablaba con la API por `fetch` a mano porque el SDK era ESM y el backend es CJS en cPanel; **desde la 6.x el SDK se publica con build dual** (`dist/index.cjs` bajo la condición `require`, `engines: node >=20`), así que `require('resend')` resuelve en el `dist` compilado. ⚠️ **Al subir la versión del SDK, comprueba que sigue siendo así** — `node -e "require('resend')"` sobre el `dist` — porque volver a ESM rompería el arranque en producción, no el build. El SDK no declara `signal` en sus opciones de petición pero las vuelca en su `fetch` interno, y el adaptador aprovecha eso para cortar a los 10 s: si un día dejara de pasar, el correo seguiría saliendo y sólo se perdería el corte. Un fallo de envío se registra y **no tumba la operación de negocio** — si el dominio no está verificado, el correo no sale y sólo lo verás en el log.
