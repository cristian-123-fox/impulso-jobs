## Source of truth

**[AGENTS.md](AGENTS.md) is the authoritative spec** — architecture, folder structure, domain map, security/RBAC model, conventions, and Definition of Done all live there. Read it first and follow it. This file only records where the current repo **diverges from that target** and the concrete commands, so it does not repeat AGENTS.md.

## Current state vs. the AGENTS.md target

AGENTS.md describes the **target**. These are the deliberate, still-standing divergences (structure and layering inside each app already follow the spec):

- Apps live in **`backend/`** and **`frontend/`**, not `apps/api` / `apps/web`. There is **no pnpm workspace root** and no `packages/api-contract` — each app is installed, built, and tested on its own (`cd` into it), and there are no root-level scripts. The frontend therefore **hand-writes its API types** under each feature's `models/` (see `core/models/api-response.models.ts`), derived from the Swagger.
- The backend DB layer supports **MySQL *and* PostgreSQL**, chosen at runtime by `DB_TYPE` (MySQL/cPanel is the live deployment). IDs are **app-generated UUID v4 stored as `varchar(36)`** (`common/entities/base.entity.ts`) so the schema is portable — no `uuid` column type, no DB extension.
- Password hashing uses **`bcryptjs`** (pure JS), not `bcrypt` — chosen so cPanel needs no native build.
- **Response envelope** is `{ success, statusCode, message, content }` / `{ success, statusCode, message, errorCode?, errors[] }` (`common/types/api-response.types.ts`), not the flat shape in AGENTS.md §6. `errorCode` comes from `common/types/error-code.enum.ts` and is the stable contract the frontend switches on.
- **Catalogs are not a `modules/catalogs/` group.** MX states/municipios, SAT tax regimes, CFDI uses **and the 23 professional areas (T15)** are embedded constants in `backend/src/common/catalogs/` (mirrored in `frontend/src/app/shared/catalogs/` — `mx.catalogs.ts`, `professional-areas.catalogs.ts`); `languages` is an entity inside `modules/candidates/`. Professional-area ids are stable and never reordered; their `slug` feeds the SEO landings (`/trabajo/<area>-en-<estado>`).
- `POST /auth/register` lives in its own **`modules/iam/registration/`**, not inside `iam/auth/`.
- **Autorizar exige rol *y* permiso.** `@RequirePermissions` dice *qué* se puede hacer, pero varios roles comparten un permiso —una empresa tiene `companies.read` y `company_users.manage` sobre **la suya**—, así que por sí solo no separa el back-office del autoservicio. Los tres controladores `/admin/**` llevan además `@RequireRoles(Role.ADMIN)` + `RolesGuard`; sin eso un EMPLOYER listaba todas las empresas y leía el equipo de la competencia. **Todo endpoint nuevo bajo `/admin` debe llevar los dos.** El gemelo autoservicio de `/admin/companies/:id/members` es `company/members`, donde la empresa **nunca viaja en la URL**: se resuelve de la sesión (`resolveOwnCompanyId`), y gestionar el equipo pide además rol interno OWNER/ADMIN.
- Frontend adds areas AGENTS.md does not list: **`features/candidate/`** + `layout/candidate-layout/` (el área real del candidato: `/candidato/{perfil,cv,postulaciones,guardadas,configuracion}` — sustituyó al prototipo `/panel`, eliminado en la Parte A) and **`features/company/`** + `layout/company-layout/`. `ROLE_HOME`: admin → `/admin`, empresa → `/empresa/vacantes`, candidato → `/candidato/perfil`.
- **El detalle público es `/vacantes/<uuid>-<slug>` (T16).** La ruta sigue siendo `:id`; el UUID son los primeros 36 caracteres del parámetro y el slug es sólo SEO. Construye links con `vacancyPath()` de `shared/utils/seo.ts`, nunca a mano.

### What is built (Aug 2026)

- **Backend** — `modules/`: `iam/{auth,users,roles,permissions,registration,account}`, `candidates`, `companies`, `vacancies`, `applications`, `talent`, `billing`, `audit`. 28 controllers, 55 use-cases, 21 migrations, 37 unit specs. Swagger at `/docs` + `/docs-json`, global prefix `/api/v1`. Includes screening questions (M15/T10), denuncias (T12), vacante enriquecida con área/contrato/escolaridad/plazas/comisiones/fecha límite + filtros y orden públicos (T15), vigencia con `expires_at` + job (T20), contador de vistas con eventos + consolidación (T18), snapshot del CV al postular (T19) y vacantes guardadas del candidato (T17 fase 1, permiso nuevo `saved_vacancies.manage`).
- **Not built** — the **Stripe adapter** (billing itself is done; payments go through `PaymentProviderPort`, today bound to `ManualPaymentAdapter`), notifications, CFDI, AI, `sitemap.xml`, T17 fases 2+ (ocultar/seguir/alertas). No e2e tests yet.
- **`candidates/` vs `talent/`** — `candidates/` is the applicant's self-service over their own data; `talent/` is the company-facing side (searching third parties, consuming purchased visit quota). `talent/` owns `talent_access_grants`/`talent_access_views` and the *consumption*; `billing/`'s `EntitlementService` does the *granting* when a payment settles.
- **Payments go through a port.** `billing/` never imports Stripe: it depends on `PaymentProviderPort`, bound to `ManualPaymentAdapter` in `billing.module.ts` (same pattern as `MAILER_PORT`). Every payment — webhook, manual confirmation or reconciliation — funnels through `SettlePaymentUseCase`, which owns idempotency (`processed_payment_events`) and activation. Writing `StripePaymentAdapter` is a one-line binding change.
- **Frontend** — public portal (home, vacantes con SSR + landings `/trabajo/...`, planes, nosotros, contacto, faq, mantenimiento), auth (login, registro empresa/candidato, reset, verificación), `/admin` (usuarios, empresas, roles, planes, denuncias), **`/empresa` completo** (vacantes, postulaciones, candidatos, promociones, usuarios, perfil) y **`/candidato`** (perfil, cv, postulaciones, guardadas, configuración). **Todo el back-office edita en `ij-modal`**, no en páginas de formulario: el detalle en ruta propia queda sólo para lo que no cabe en un diálogo (matriz de permisos del rol, equipo de la empresa). UI kit is `ij-{input,select,multiselect,autocomplete,datepicker,textarea,modal,badge,button,icon,logo,pricing-card}` — **no** `ij-table`/`card`/`pagination`/`tabs`/`spinner`/`empty-state` yet (admin uses a local `admin-pagination`, panel a local `data-table`).

## Commands

Both apps use pnpm. Backend on `:3000` (`/api/v1`, docs at `/docs`), frontend on `:4200`.

- **Backend** (`cd backend`): `pnpm run start:dev` (watch) · `pnpm run build` · `pnpm run start:prod` (`node dist/main`) · `pnpm test` — single test: `pnpm test -- app.controller` or `pnpm test -- -t "name"` · `pnpm run test:e2e` · `pnpm run lint` · `pnpm run format`
- **Backend DB** (`cd backend`): `pnpm run migration:run` · `pnpm run migration:revert` · seeds `pnpm run seed:rbac` (roles + matriz de permisos), `seed:admin`, `seed:candidate`, `seed:company`, `seed:applications` (catálogo de estados de postulación). Each has a `:prod` twin that runs the compiled `dist/` version. **Re-run `seed:rbac` after adding any permission code** — the guard reads the DB, not the source list. `seed:applications` is required for M11 to work at all: without it there is no status to assign; `seed:plan-features` likewise for M14 — it seeds the 13 benefit codes but **no plans**: prices in MXN are a business decision, captured in the back-office (`/admin/planes`, sobre `POST /admin/plans`).
- **Jobs de cron** (`cd backend`, ninguno está agendado — engánchalos a cron, cada uno tiene gemelo `:prod`): `pnpm run billing:expire` (caduca promociones y revierte distintivos) · `pnpm run vacancies:expire` (T20: cierra vacantes con `expires_at` vencido; la vigencia nace de `VACANCY_LIFETIME_DAYS`, default 60, 0 la desactiva) · `pnpm run views:consolidate` (T18: suma `vacancy_view_events` a `views_count` y borra los eventos — la UI dice "se actualizan una vez al día").
- **Account purge** (`cd backend`): `pnpm run purge:accounts` hard-deletes soft-deleted accounts past `ACCOUNT_RETENTION_DAYS` (default 90). **Dry-run by default** — it only lists; add `-- --confirm` to actually delete. It is not scheduled; run it manually or from cron.
- **Frontend** (`cd frontend`): `pnpm start` · `pnpm run build` · `pnpm test` · `pnpm run serve:ssr:frontend`

## Tooling notes (not in AGENTS.md)

- **Path aliases** use `@/` in both apps but with **different targets** — Backend: `@/*` → `src/*` (resolved by the Nest CLI at build, no `tsc-alias`; Jest via `moduleNameMapper`). Frontend: `@/*` → `src/app/*` (resolved by the Angular build from `tsconfig.json` `paths`). Prefer `@/…` over `../…` for cross-directory imports; keep `templateUrl`/`styleUrl` relative (the alias does not apply to component resource URLs).
- **pnpm 10 blocks native build scripts.** Approved ones are pinned per app under `package.json` → `pnpm.onlyBuiltDependencies` (backend: none — the list is empty on purpose, there are no native deps; frontend: `esbuild`, `@parcel/watcher`, `lmdb`, `msgpackr-extract`). When adding a native dep, add it there and run `pnpm rebuild <pkg>`.
- **Frontend SSR (reactivado en T16):** `src/main.server.ts` must pass the `BootstrapContext` to `bootstrapApplication` (required since Angular 20.1) or the build fails at route extraction with `NG0401`. `/auth/**` and the rest of the public shell are prerendered — API calls on init go inside `afterNextRender` — **except** `/vacantes`, `/vacantes/:id` and `/trabajo/:landing`, which are `RenderMode.Server`: they fetch on the server and hand the data to the client via `TransferState` (see `vacancies-page.ts` / `public-vacancy-detail-page.ts`; browser-only work like compartir/mapa/preguntas stays in `afterNextRender`). **`security.allowedHosts` en `angular.json` es obligatorio** (hostnames sin puerto): sin el host listado, el motor SSR de Angular 20 lo rechaza y sirve CSR silenciosamente. SEO por vista con `core/services/seo.service.ts` (title/meta/OG/canonical/JSON-LD).
- **cPanel:** the frontend deploys as a **Node SSR app** (`dist/frontend/server/server.mjs`; opción estática documentada pero pierde SSR) and the backend as a Node app on a subdomain — see [DEPLOY-CPANEL.md](DEPLOY-CPANEL.md). Set `DB_TYPE=mysql` with `DB_SYNCHRONIZE=false` in production and run `migration:run:prod` + the `:prod` seeds. **No SMTP yet** — `MAILER_PORT` is bound to `ConsoleMailerAdapter`, which logs the verification/reset link instead of sending it. Swap the adapter binding in `auth.module.ts` when credentials exist.
